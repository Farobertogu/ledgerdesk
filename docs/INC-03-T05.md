## Response-observation correction and learning

Two independent test-harness defects were isolated with small real HTTP/browser controls. In Playwright 1.63.0, the client-side `Response.finished()` promise can remain pending after `requestfailed`. Body/JSON retrieval uses a different completion path and rejects that failure, but still depends on DevTools body retrieval. Later hosted runs exposed `net::ERR_ABORTED` in that retrieval for successful preparation POST observations. This identifies an observation failure; it does not establish the transport cause or prove that the application received a complete body.

The [passive body observer](../tests/intake/ui/lookup_body.mjs) now records only bytes returned by the application's existing reader. It preserves the native fetch/read promises, response and reader, with no clone, replay, mock or extra read. It accepts only a completed, bounded body with consistent length and valid JSON, associated with the exact request and retained operation. Cancellation, read failure, missing chunks or overflow before completion fail the observation. An abort after verified completion does not undo delivered bytes; current-session adoption remains a separate UI assertion. Preparation save, inspection, proposal and confirmation use this same rule, with their original content, reference and SQL assertions intact. Deliberate W13 response-loss injection remains distinct from successful response observation.

The [shared response holder](../tests/intake/ui/response_hold.mjs) also distinguishes successful continuation from cancellation of the exact retained Network request. Only that request's explicit cancelled `net::ERR_ABORTED` event permits its obsolete interception to be classified as cancelled; unrelated protocol errors still fail. W19/W20 retain their seven-second hold budget, successful-response control and no-adoption assertions. Later cases stop after a primary error or parent cancellation, while cleanup still runs. The existing 15-second body, 180-second group and 240-second outer limits were not increased.

The first repair covered lookup but left confirmation on the same failing observation path; reviewing the relevant equivalent uses of that mechanism together avoids successive partial repairs.

The practical rule is to choose the observable that proves the assertion: headers do not prove a body, DevTools retrieval does not prove application consumption, and consumption does not prove permitted UI adoption. Before another timeout change or retry, retain the first failure and use a small complete/truncated/cancelled/foreign-request control to discriminate these states. Diagnostics must remain bounded and allowlisted; raw bodies, credentials and arbitrary error prose are not public evidence.
