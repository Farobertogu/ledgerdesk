# INC-01 T05 · Integrated synthetic reading

## Scope and topology

The existing Next `/material` viewer reads directly from the standalone reading
terminal, which reads a fresh PostgreSQL 16 trial through `PgReadingStore`.
There is no Next proxy, replacement renderer, live model call, historical data
migration or production identity. The public profile remains `reading/1`.

T05 changes transport configuration and browser access, not projection policy,
the persistence port, SQL schema or the admission mechanism accepted in T04.
The Next material API routes still refuse successful reads. This is a local
integration candidate; review and publication are separate steps.

## Configuration and trust boundaries

| Process | Setting | Meaning |
|---|---|---|
| Next | `LEDGERDESK_READING_SERVICE_ORIGIN` | Exact destination passed to the viewer; no request-time URL parameter or default fallback |
| Terminal | `LEDGERDESK_READING_UI_ORIGIN` | Browser origin allowed to read responses; not a subject, role or permission |
| Both | Existing explicit local-synthetic gate | Disabled unless the server configuration is valid |
| Terminal only | Existing dedicated PG URL/port and synthetic context | Never passed to the browser or reused from historical identity |

Both origins require `http://127.0.0.1:<port>`, with a canonical explicit port
between 1024 and 65535. Paths, credentials, query strings, fragments, DNS names,
alternate IP spellings and wildcards are rejected. For example, Next may listen
on 3180 and the terminal on 3002: two origins, both loopback. A missing/invalid UI
destination produces a closed setup page. Invalid terminal UI configuration
fails before storage connection. An unconfigured terminal refuses Origin.

The viewer sends GET with credentials omitted, no-store and redirect rejection.
Only the public destination is serialized by Next; subject, generation, database
connection, material and receipts are not page props. The terminal sets Vary:
Origin. Exact allowed Origin receives Access-Control-Allow-Origin on successful
and problem responses, never `*` or Access-Control-Allow-Credentials. Disallowed
or opaque Origin receives 403 before preparation and no CORS read permission.

CORS is not authentication or a local-process security boundary. A raw client
can forge or omit Origin but cannot thereby change the server-owned context or
policy. Simple GET requires no preflight or extra method. A browser CORS failure
is a technical presentation failure, not a readable 403 body; raw HTTP tests
separately verify the terminal's 403. This is not safe public identity handling.

## Executable evidence

`tests/reading/test_T05_integration.mjs` uses a production Next build, actual
Chrome/Chromium, the real terminal, PG adapter and a disposable cluster. No route
is fulfilled with a fabricated response. I14 delays an actual fetched Response
and ignores A's abort signal, so late-selection protection cannot rely on
transport cancellation. Its original still comes from the real service.

`test:reading:mutations` separately checks six deliberate defects in memory:
port bounds, foreign-Origin admission, wildcard CORS, destination fallback,
credential inclusion and loss of the late-selection guard. Every baseline must
pass first. Import/parse errors do not count as behavioral detection. These are
module-level negative controls, not six additional PG/browser experiments.

The suite checks SQL receipts and writer lock waits, not just rendered labels.
Next uses an exclusive test port and a counted legacy-DB trap. BUILD_ID, its
modification time and size are checked at setup, each scenario and completion.
The exact child must report readiness; no unrelated server is reused. The trap's
PID labels the active test server, not a proven caller. Any hit fails the run.

Resources are registered for cleanup before further setup. Observer gates and
process closes are bounded; handled failures attempt all cleanup steps. PG
removal validates ownership and verifies that the test project's container,
volume and network are gone. This does not guarantee cleanup after a machine
crash or loss of Docker itself.

## Reproduction

Use installed dependencies, a production build and Docker's Linux engine:

```text
npm run test:reading:origins
npm run test:reading:mutations
npm run build
npm run test:reading:integration
```

Install the configured Playwright browser if absent. Locally,
`READING_BROWSER_CHANNEL=chrome` selects installed Chrome; CI installs bundled
Chromium. Run the whole file: filtering only a nested scenario may skip the
parent that creates the environment and is not integrated evidence.

The suite creates its own seed/context/credentials and never needs a historical
database. Real screenshots go to ignored
`test-results/reading-integration/desktop.png` and `mobile.png`. Images prove
visible layout; exact text, SQL and network assertions carry those other claims.
CI runs integration after the existing browser tests and uploads these images.
A configured job is not evidence of a remote run.

The separate browser-test output directory is `test-results/reading-browser`;
running the earlier Playwright suite no longer replaces the other suites'
evidence directory. The original-text stress seed deliberately includes NUL
and an isolated surrogate; font placeholders in its screenshot are not evidence
of changed stored characters. The DOM string assertion checks that separately.

## Limitations and review focus

The writer-free-expiry experiment may receive material after its deadline when
the emitter pauses after its last time check. It reports the observed status,
not a prefixed expectation of safety. Subsequent reads must reflect expiry.
Synthetic integration does not establish the unresolved physical guarantee or
authorize real-data deployment.

Review actual working-tree changes, including untracked files. Prioritize the
two origins, no credentials/proxy/fallback, SQL-before-bytes, writer ordering,
real failures, late-response protection and cleanup. Spanish source fixtures
and public opaque values are unchanged. T05 needs no package/version or lockfile
change. Publication waits for review of this candidate.

Earlier development runs are not claimed as clean. Test mistakes in the refusal
helper and alert locator were corrected, as was a browser-event expectation
that incorrectly expected a readable response after CORS refusal. Two runs also
received paired connections on the DB trap. A separate listener with no Next or
database reproduced those connections; the live TCP clients were attributed to
an unrelated local desktop application performing background port probes.
This reproduces an external source, not retrospective proof of
every prior connection. No connection was excluded from the guard, no threshold
was relaxed and the application was not stopped. The failed run at
`test-results/reading-integration-final.tap` remains failed evidence despite its
intermediate filename; the later reviewed run above is separate and clean.

All handled runs removed their synthetic PG projects. The two pre-existing
stopped containers and their volumes remain untouched. The final screenshots
were inspected at desktop and narrow widths. The SQL schema/adapter, policy,
persistence port, public profile, source fixtures and lockfile are unchanged
against the starting commit. Remote CI, PR review and publication have not run
for T05; INC-01 is not declared fully conformant or production-ready.
