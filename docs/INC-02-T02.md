# INC-02 T02 · Persistent deployment activation and sessions

## Scope

An isolated synthetic account can now be activated through the predeclared
master address, authenticated with a password, inspected through its current
session and logged out. Technical recovery replaces that account's credential
only under a current deployment-control authorization. The minimal Next UI
exercises the actual HTTPS terminal and PostgreSQL 16 service.

This is not public registration, invitation management, a grant engine, a
corpus reader or production authentication. Account, attributable person,
office, password verifier and session are separate facts. The master office
does not imply global reading, approval or authority over material.

The implementation extends accepted ADR-032's `session/1` transport; it does
not change `reading/1`. [ADR-033](../adr/ADR-033-persistent-synthetic-access.md)
records the proposed local realization. No acceptance is inferred from tests.

## Admission and persistence

The service requires exact synthetic configuration, the admitted reception
profile and the complete attributable preparation-root fields. Missing,
expired or disabled declarations fail closed. This realization supports an
explicitly expiring root; it does not certify the external mandate or implement
post-bootstrap revalidation/investiture APIs.

The HTTPS receiver acquires the shared deployment guard and checks reception
before consuming a credential body in application code. Socket/TLS/HTTP header
processing necessarily precedes that check; no claim is made that the network
stack has received zero bytes. Header limits, a 16 KiB body limit, a five-second
body timeout and sixteen active request slots bound that reception.

After parsing, the service acquires the flow/email object lock and opens one
Repeatable Read transaction. It resolves current deployment, account, proof,
session, restrictions and intentions there. Password work is bounded to two
concurrent operations; unsupported verifier parameters never reach the KDF.
Different unknown/known account paths use the same supported Argon2id work.

The effect and required evidence commit together. SQL is idle during the test's
paused post-commit handoff. Shared admission remains held through the terminal's
synchronous response handoff. Logout and technical recovery take exclusive
admission; separate control functions coordinate deployment availability and
account restriction using the same lock. There is no mid-operation upgrade.

Subsequent transport observations are append-only. `handed_off` means that the
terminal submitted the response to its transport API; it is neither a socket
completion nor human receipt. A post-commit interruption does not rewrite the
prior decision into a denial. Observation failure cannot unsend a response.

The finite writer inventory is deliberately narrower than the complete system:
grant/support/material/policy writers are not implemented here. Database owner
or superuser interference is outside the runtime-role guarantee. Those trusted
credentials are used only to set up the disposable test and inject faults.

## The four implementation requirements

### Account non-enumeration

Login returns the same public denial for an unknown address and a known address
with an incorrect password. Unknown or unsupported verifiers execute the fixed
decoy verification rather than taking a quick return. Activation and recovery
challenge reception both return generic acceptance with identical public
status, body and headers; eligibility changes only the controlled mailbox.

The experiment compares whole HTTPS responses, with alternating class order,
12 warmup rounds and 128 retained samples per class. It reuses the existing
`TIMING_PROTOCOL` and `compareTiming` without changing their thresholds. Login
attempt counters are reset equally between measured attempts; separate tests
exercise real rate limiting. Challenge counters are likewise reset equally to
measure eligible/ineligible reception rather than resend suppression. Activation
is measured before account creation, and recovery during an authorized window.
A deliberately shifted control must be detected.

This is a finite detector, not a promise of constant-time network behavior or
universal non-enumeration. Random proof identifiers, malformed requests, exhausted
limits and saturation are separate populations, not silently pooled into a
single passing average. No timing threshold is retuned after a failure.

### Login abuse isolation

The small budget is scoped to (email, actual socket peer): five attempts in the
300-second fixture window. A separate per-email budget admits at most ten times
that number, 50, across peers. The first budget is checked first; a refused peer
cannot spend the aggregate by sending more requests. Both checks remain under
the email object lock and the decision transaction. Successful logins also
consume an attempt. The two fixed windows start independently and rejected
requests do not prolong them. Cookies, intentions and restarts cannot reset them.

Only `remoteAddress` supplied by the TLS socket contributes the peer; `Origin`,
`Forwarded`, `X-Forwarded-For` and `X-Real-IP` are not peer identities. No reverse
proxy or forwarded-address trust policy is introduced. The HTTPS tests bind real
loopback source addresses inside the isolated container; they do not inject a
claimed peer into the service.

The aggregate ceiling deliberately preserves a finite bound against distributed
password guessing. It is larger than the former five-per-email budget: the
trial trades additional bounded attempts for isolation between peers. This is
not a final production policy. Shared-address users can still affect one another,
and enough peers can exhaust the aggregate and deny even a correct password.
Continued abuse can exhaust later windows. These conditions return `rate_limited`,
not `unauthenticated`, and do not restrict the account or alter its verifier.

A16 covers the shared-address residual, fresh-cookie and forged-forwarding
negatives, persistence across service restart, and a different peer's successful
login. A17 exhausts the aggregate for known and unknown addresses and compares
their public refusals. Expiry is directed by aging only the stored window start
past the configured duration; the test does not wait five minutes or change the
production clock. A19 races the last available peer slot and requires exactly
one admitted denial and one rate limit, with no counter overshoot.

### Demonstration surface

The real-browser demonstration stays inside a disposable container. Its Next
server serves the same `AccessPanel` used by `/access`; the browser calls the
actual terminal, which persists in the isolated PostgreSQL database. The
controlled test mailbox supplies the bound activation code out of band.

The container owns its temporary TLS authority, NSS trust and test-name resolver.
It has no host network ports, mounts or external network at execution time.
Nothing edits the host's hosts file or trust store. No long-lived service is
left running. Screenshots show the real session on desktop and narrow screens,
and the signed-out form. This delivery does not provide an interactive host demo.

### Persisted CSRF and session rotation

The provisional flow and authenticated session each store an independent random
CSRF value. Login rotates the credential/CSRF pair and invalidates the provisional
flow. Cross-session, stale and fabricated tokens fail without terminating the
legitimate session. Reload asks the server for the current session; it does not
read a cached client role. Cookies are host-only, Secure, HttpOnly and SameSite
Strict. Session-cookie lifetime matches the persisted session, not the shorter
pre-authentication flow. JavaScript stores neither session credentials nor
passwords in localStorage/sessionStorage.

Cookie projection uses separate `Set-Cookie` fields, never a shared string slot
or comma concatenation. It preserves both session and flow cookies, including
session deletion, with independent lifetimes and unchanged security attributes.
A18 exercises that projection over real HTTPS on a separate serialization probe;
no T02 route is modified to fabricate a dual-cookie operation or implement T03.

### T02 idempotency and uncertain outcomes

Every admitted POST requires `x-ledgerdesk-intent`. Its namespace includes the
route and current flow/session binding. The database stores an HMAC of canonical
request fields rather than plaintext passwords or codes. Same intention plus
different payload conflicts. Activation/recovery receipts can be reconciled
under the still-valid flow and current restriction/recovery policy; the effect
is not reapplied. Competing uses serialize and transaction conflicts retry only
within the declared bound.

The UI preserves its pending intention after a 5xx or lost response, not only
after a dropped connection. A13 repeats a committed recovery from the actual
form and checks that the account revision changes only once.

Login never replays a session secret: a used provisional flow is invalid, and
an uncertain client checks its current session before attempting another login.
Logout invalidates its session; a subsequent attempt is denied rather than
reviving it to replay a receipt. The general operation-result endpoint remains
T03, not a partially implemented route in T02.

The local mailbox is an injected adapter. It records delivery/failure separately
from the generic accepted HTTP result. No external SMTP or durable message queue
is implemented. A service crash can require a fresh bounded challenge request;
idempotent acceptance does not promise eventual email delivery. Ordinary evidence
contains no raw password, session credential or email code.

## Reproduction

Run from the repository with Docker available:

```text
npm run test:access
npm run test:access:runtime:unit
npm run test:access:runtime
node ci/access_runtime_check.mjs --mutation=drop-decoy
node ci/access_runtime_check.mjs --mutation=drop-csrf
node ci/access_runtime_check.mjs --mutation=drop-origin
node ci/access_runtime_check.mjs --mutation=drop-intent
node ci/access_runtime_check.mjs --mutation=drop-proof-consumption
node ci/access_runtime_check.mjs --mutation=drop-login-peer
node ci/access_runtime_check.mjs --mutation=drop-login-account-limit
node ci/access_runtime_check.mjs --mutation=drop-session-cookie
node ci/access_runtime_check.mjs --mutation=early-failure
```

Baseline must exit zero. Each mutation is expected to fail at its named behavior,
not merely at compilation or setup. The early-failure mode instead proves cleanup
after injected startup failure. All use the same real terminal and isolated
database. Each owned container has a unique label; the harness checks ownership
before removing it and does not remove historical containers or volumes.

The base Node and Playwright images are pinned by digest. PostgreSQL is installed
as package `postgresql-16` and runtime checks enforce major 16; the package patch
release is not locked by the Dockerfile. No claim of bit-reproducible OS packages
is made. Image building requires package/image downloads; execution is offline.

Outputs: `test-results/access-runtime/<baseline-or-mutation>/run.log`, three
timing JSON reports and PNG captures. They are local generated evidence, ignored
by Git, and the runtime outputs are uploaded by CI when it eventually runs.

## Correction verification · 2026-09-10

This pass changes `service.ts`, the terminal's cookie projection, the runtime
tests and mutation runner, and their documentation. It does not change the SQL
schema, database adapter, password verifier, access-route schema, UI behavior,
`reading/1`, ADR-032 or the dependency lockfile. ADR-033 remains proposed.

The final formatted source package passed the real PG16/HTTPS/Next/browser suite:
**21/21 including the parent**, 51.21 seconds. A16–A19 are new directed scenarios;
the pre-existing cases remain present. Runtime unit tests passed **5/5**, including
the dual-cookie projection, independent expiry attributes and session deletion.
Contracts/security passed **74/74**. Retained reading suites passed **126/126**,
**16/16**, **11/11**, **50/50**, **7/7**, **4/4** and **6/6**. Types, both import
boundaries (96 and 121 modules) and local repository checks passed.
The retained T01 browser transport passed **17/17**, and the retained PostgreSQL
reading service passed **25/25**, with its owned-cluster cleanup marker.

The final baseline measured login medians of **86.47 ms** for an unknown address
and **86.96 ms** for an incorrect password at the declared address. Activation
medians were **10.39 / 10.20 ms**, and recovery **10.34 / 10.43 ms**. No signal was
detected under the unchanged finite protocol; the shifted control was detected.
These measurements do not assert constant time or universal non-enumeration.

All eight behavioral mutations ran against that same source package, sequentially
to avoid adding parallel test load to timing measurements. Each exited 1 because
of the named behavioral assertion, not a build or setup failure:

This local correction pass did not repeat the full host application build or the retained HTTP/viewer browser
integration. The real access UI was rebuilt and exercised inside the runtime

do not confer ADR acceptance, authorize merge or implement T03.
