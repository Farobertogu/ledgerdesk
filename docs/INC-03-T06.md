### Post-merge controller-loss cleanup

[PR #39](https://github.com/Farobertogu/ledgerdesk/pull/39) passed its final-head
[workflow 35745751322](https://github.com/Farobertogu/ledgerdesk/actions/runs/35745751322)
on attempt 1, with all 19 jobs successful, and merged at
`5b7b429a1a0233a4708952bdf2dfdfc6522ad7b2`. The
[actual-main workflow 35748099696](https://github.com/Farobertogu/ledgerdesk/actions/runs/35748099696),
attempt 1, failed: `controller-loss` passed 5/5 runtime checks, but command 124
could not remove an image referenced by a container. Only 10/22 recorded resources
were marked cleaned. The mandatory `reading` result also failed because this producer
failed. The other 17 jobs passed. This failed run remains failed.

The unchanged local selector passed 5/5 with 22/22 resources removed. A deterministic
execution of the unchanged controller-loss source then exposed a separate, concrete
cleanup defect: a worker that exits between inspection and `kill` causes that command
to fail; the old cleanup skips removal and its diagnostic write. This modeled
interleaving does **not** establish the historical hosted cause: the public artifact
does not identify the blocking container or the internal controller error.

The localized harness correction reinspects exact container identity, image, owner
and name after an unsuccessful kill, and requires a stopped, zero-PID, non-restarting
state before removal. A running or changed-identity target still fails. Cleanup
diagnostics survive a failed removal, and an unexpected controller setup/cleanup error
is no longer accepted as the deliberately injected controller loss. The service's
uncertain state does not become a successful producer termination.
