## Original storage and recovery

The prototype uses a real PostgreSQL control record and private object volume.
Files are created without overwrite and synchronized before controlled
finalization. Runtime and observer roles differ; invalid object selectors and
unauthorized writes are rejected. Exact returned bytes, length and digest are
checked independently. The sample uses a 1 MiB object cap, 64 MiB logical object
budget and 32 logical operations, with rejected reservations not resetting
existing intent history.

The filesystem and database are not claimed to share an atomic transaction.
Faults cover a file retained before SQL commit, a completed effect whose reply
is lost, interrupted transfer with the SQL session idle, restart with the same
volumes, stale generations and explicit bounded resume. Two separate database
channel interruptions occur before versus after COMMIT: the observer checks
the actual durable state after terminating the backend. A connection error
alone is never interpreted as permission to repeat an effect.

Restore uses separate owned destination storage and verifies pending and
completed control records, exact objects and availability. An orphan partial
file is not promoted to a receipt by the backup format. Corruption is reported
as unavailable instead of returning changed content. These are process/engine
experiments, not simulated power failure or proof about every physical disk.
No real session, receiving authority or protected original handoff is exercised
by this prototype.
