# INC-02 T01 — Access foundation and transport experiment

## Scope

This delivery prepares executable access contracts and demonstrates the accepted
browser transport before implementing accounts. See `docs/access-contract.md`
for the exact boundary, route bindings, pending admission, security configuration,
persistence design and capability inventory. The ADR-032 session amendment was
accepted on 2026-09-09; the original credential-free profile is preserved.
Acceptance is limited to this synthetic foundation and transport experiment,
not production use or completion of INC-02.

The actual `/material` page, material DTO, old credential-free reader, terminal,
policy, persistence port, PostgreSQL adapter and SQL schema are unchanged.
The new server guard is consumed only by a fixture. No real account, database,
email provider, material or production route is introduced.

## What the experiment runs

`npm run test:access:browser` builds a narrowly allowlisted Docker context:
package manifests, access contracts/guard and the experiment. No `.env`, Git
metadata, private document, existing database or full repository is copied.
It builds a neutral Next fixture in production mode with the installed Next
version. It does not build or simulate the finished account UI.

Inside one disposable Linux container, a real browser communicates with a real
HTTPS Next listener and a separate HTTPS terminal. The terminal owns the
response, not a Next proxy. All servers bind container loopback. Runtime
networking is disabled, no host ports/volumes are published, and no database is
started. A second host simulates an unrelated same-site service; two further
listeners present deliberately invalid TLS credentials. The fixture contains
only synthetic in-memory provisional/session state and one effect counter.

The container pins Node 22.16.0 and Playwright 1.63.0 images by digest. The
test creates one-day certificates and an NSS trust database in the disposable
container user's home, not the host user's trust store. A browser-only resolver
maps the trial hosts to container loopback. No global hosts file, machine-wide
CA, `ignoreHTTPSErrors`, certificate-ignore flag or HTTPS verification bypass is
used. The successful good certificate and two distinct certificate-error
controls are prerequisites to calling this a transport proof.

The browser is headless and uses Playwright's default sandbox configuration
inside this isolated fixture. This is not a browser-sandbox certification.
Dependencies/image builds need network access; the test runtime does not.
The initial image download/build can cost substantially more than the test.
Build and container execution have independent finite deadlines (15 and 3
minutes). Cleanup targets only the unique container name with its matching
ownership label. This is bounded cleanup, not a claim that any host failure can
never leave a resource behind. Images/build cache remain reusable on Docker.

## Transport assertions

| ID | Actual observation required |
|---|---|
| B01 | Production-built Next serves only the neutral shell, without session/material data |
| B02 | The synthetic provisional cookie is host-only, Secure, HttpOnly, Path=/ and Strict; script on its own terminal host cannot read it |
| B03 | Missing CSRF causes the preflight to fail before POST; wrong CSRF is rejected by the operation; provisional state cannot read; a valid login-like transition rotates the cookie |
| B04 | The session request reaches the terminal with credentials; deliberately omitting them produces 403, not a fallback |
| B05 | Valid credentialed preflight and correct independent CSRF produce exactly one effect; incorrect CSRF produces none |
| B06 | Actual requests to Next and an unrelated same-site service carry no terminal session cookie; browser CORS blocks that service's protected request despite its knowledge of the test CSRF value |
| B07 | Browser CORS blocks an opaque sandboxed iframe's protected request |
| B08 | A trusted certificate with the wrong SAN and an untrusted issuer fail with their respective certificate errors before any HTTP request reaches those listeners |
| B09 | After session establishment, no session/CSRF value enters Next SSR or browser storage; the effect count remains exact |
| B10 | Clicking activation/recovery links on another registrable site reaches the UI without the API cookie, then a same-site terminal fetch succeeds |
| B11 | Direct Node HTTPS, against the same terminal with the current browser-established cookie and valid CSRF, produces one effect for an allowed Origin and none for foreign, missing or `null` Origin; positive controls surround the denials |
| B12 | The actual HTTPS preflight response has exactly POST, the three declared request headers and a 60-second Max-Age; it produces no effect |

Activation/recovery checks here include actual cross-site link navigation from
`mail.mailbox.test` back to the UI with synthetic flow markers, followed by a
direct terminal read. They do not prove email delivery, real recovery, account
binding or session persistence; those belong to T02/T03. The new helper supplies
transport defaults, not a complete administrative HTTP client.

B06/B07 prove browser enforcement of CORS, not independent server admission.
B11 has no browser CORS layer and proves the latter. Its Node client validates
the ephemeral CA and the terminal hostname, keeps certificate verification
enabled and has a five-second request deadline. Origin is still a declared
header, not a non-browser identity: clients can forge it, and valid credentials
and authorization remain separate requirements.

## Corrections during the experiment

The first Docker invocation could not read an in-use Docker context file; it
failed before a container started. A later invocation used the unchanged
Docker configuration successfully.

The first browser run was **failed**, not evidence of conformity. Its missing-
CSRF assertion expected an operation-level 403 although the exact header
preflight rejected the request earlier. It also continued after that failed
setup and waited on closing a certificate-error page until the outer timeout.
The corrected assertion proves that the POST never happens; incorrect CSRF
still reaches and fails the separate operation check. Certificate controls
wait for navigation commit/rejection and leave failed-navigation page cleanup
to the browser's final cleanup. No threshold or certificate check was relaxed.

## Directed transport and lifetime checks

The original unit mutation already detected removal of the shared Origin guard;
the browser experiment did not. Removing that guard leaves B01–B10 green because
CORS still blocks the foreign browser. B11 now sends direct HTTPS with the same
valid cookie and CSRF. Its allowed-Origin control succeeds; changing only Origin
must produce 403 and leave the effect count unchanged. Missing and `null` origins
are also tested, followed by another successful allowed-Origin control.

The preflight response now comes from `preflightHeaders(config)`. The receiving
guard and the response share the request-header allowlist; the fixture no longer
owns a duplicate. Exact unit and wire assertions cover the response. Three new
mutations widen the headers, widen the methods or extend Max-Age; each must fail
its independent assertion. Cached preflight permission does not bypass the
actual request's Origin, session or CSRF checks.

The required `invitationSeconds` setting has a 1–604,800-second trial range;
the synthetic fixture chooses 86,400 seconds. `invitationExpiryAllowed` checks
the requested absolute expiry against the server's issuance time, in milliseconds.
Tests cover the exact bound, one millisecond beyond, nonfuture expiry, malformed
times, unsafe arithmetic inputs, a one-second configuration and missing/invalid
configuration. T03 remains responsible for using this check at issuance and
rechecking the stored absolute expiry at acceptance. Proof renewal and resending
do not extend invitation validity. No invitation service is claimed in T01.

## Explicit residuals

- This delivery does not implement T02 or activate the session profile in a
  production route.
- Contract validity is not evidence of route admission, authority, account
  uniqueness, exact proof/session binding, atomic persistence or permission
  correctness. Those have named consumers in the contract document.
- The tables above record local runs. Remote execution evidence belongs to the
  pull request's checks; those tables do not establish a remote result or cover
  browser/OS combinations outside the tested Chromium image.
- Full writer-free-expiry conformity remains open. This experiment has no
  protected material and does not exercise or close that property.
- Dependency auditing reported existing Next 16.3.1 (critical) and transitive
  sharp (high) advisories. The new Argon2 package introduced neither report;
  the Next/sharp versions are unchanged. No audit-fix/force operation was
  applied. These require a separate directed dependency update and regression
  pass before network exposure or real credentials. The isolated runtime here
  has no network, real secrets, image-upload API or user database.

The advisory record is reproducible with `npm audit --json`; its report can
change with the advisory database. At this check it named
GHSA-p293-qw3h-jr36, GHSA-2xp9-vwfh-vxw4 and GHSA-rgj7-g3m4-5g8c.

## Reproduction

Run `npm ci`, `node ci/access_boundary_check.mjs` and `npm run test:access`.
With Docker running, run `npm run test:access:browser`. The old-profile
comparison is `npm run test:reading:origins` and
`npm run test:reading:mutations`; their assertions have not been edited.
The standard type, build and relevant reading checks still apply.

To reproduce the integrated negative control, run
`node ci/access_transport_check.mjs --mutation=drop-origin`.
This invocation **must exit 1 at B11** with the status/effect mismatch recorded
above, while B01–B10 pass. A timeout, setup failure or unrelated assertion is not
evidence that the mutation was detected. Run without the flag for the unmodified
baseline. The mutation has no source-file or production configuration counterpart.

The trust setup follows Chromium's
[Linux certificate documentation](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/linux/cert_management.md);
the image/runtime separation follows the
[Playwright Docker documentation](https://playwright.dev/docs/docker).
