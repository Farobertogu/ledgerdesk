# INC-02 · T05 · Effective administration

## Scope and delivery boundary

Local implementation on `card/INC-02-effective-administration`, based on `d182c75`.
This is the bounded administration presentation for the synthetic access trial,
not an authority-management product or whole-increment acceptance. ADR-036 remains
proposed. No commit, publication, remote CI or merge is established by this report.
T06, real data, external mail and production use remain outside scope.

The journey uses the real Next interface, HTTPS terminal and isolated PostgreSQL
16. It connects the existing identity, invitation and nominal-census producers;
no demonstration role provider or browser-computed permission decision is added.

## What changed

### Capabilities without additional disclosure

`access_presentation.ts` defines a closed explanation vocabulary derived only
from implementation, enablement, authorization and execution. The summary cannot
read an internal permission, investiture or support reason. The validator checks
both the closed shape and consistency with the four axes. The UI displays all
received rows, including disabled and non-executable rows, with separate axis labels.

The existing server omission of non-revealable surfaces remains before response
construction. There is no public `revealable` field, hidden-row count, private
reason or auxiliary identifier. A missing row does not explain its absence.
The new summary does not grant authority and is not an additional policy evaluator.

### Object-authorized invitation actions

`invitation_view` adds a required `available_actions` list only after the existing
inspection check. Each entry binds one closed action to its target and current
revision. Invitation actions reference the containing pending invitation; accepted
grant withdrawal references a grant already included in that view. Duplicate
offers, foreign targets and inconsistent revisions fail closed validation.

Administrative offers and executing routes reuse their management/withdrawal
predicates and the existing authority evaluator. Acceptance offers require a
current verified proof, valid pending terms, eligibility and compatibility. The
target account's restriction/office is queried after view admission in the same
decision snapshot; the authority snapshot intentionally contains no email column.
Showing a control never bypasses the next request's authority, proof, state,
expected-revision or replacement-term checks.

An authorized recipient can read terms with zero actions. A grant withdrawal can
be offered and executed even when generic invitation options are empty. No
arbitrary-object action query, direct grant route, impersonation or role editor
is introduced. The route inventory and request shapes are unchanged.

### Scoped census and interface behavior

The census UI consumes only the existing authorized page: account identifier and
display name. It does not infer email, roles, credentials or chronology from the
opaque revision fingerprint. Continuations use the existing server-bound cursor.
Old page content is cleared before a new request; failure is not displayed as a
successful empty population. Names and invitation terms remain escaped text.

The existing visual language is retained. The added capability labels, focus
indicators, status messages and narrow layout support inspection without turning
the interface into an authorization engine. The demonstration remains inside the
disposable HTTPS/browser environment; no host DNS or certificate-store change is
required. No always-running demo service is left behind.

### Exact retries, receipts and session lifetimes

`IntentionSlot` retains a cloned request body, parameters and original intention
key in memory. An uncertain invitation effect cannot be silently replaced by a
different operation. Explicit retry sends the same key and bytes, including the
already-computed expiry and expected revision. Intermediate GETs do not clear it.
This local byte-preservation mechanism is not the server's canonicalization
algorithm; `canon_m09_1` is unchanged.

An issuance returns an invitation identifier, not an operation identifier. The UI
does not invent a receipt for it. When a mutation actually returns an operation
identifier, the existing reauthorized operation route can confirm its recorded
status. A later read failure does not rewrite a confirmed effect as a failed write.

Sensitive presentation work has a local cancellation lifetime and an exact
observed session, compared with the in-memory CSRF value rather than account
identity or account revision. Capability, invitation and census adoption include
session observations. Local context replacement cancels/discards stale work;
same-account replacement sessions are tested explicitly. Refresh preserves an
unconfirmed invitation while the exact session remains unchanged. Technical 503
uncertainty is not converted into logout or a false unauthenticated result.

These checks do not establish atomic observation between the browser and server,
instantaneous cross-tab synchronization or erasure of bytes already received.
Reload/navigation or session/proof-context replacement discards in-memory state;
an unobserved effect must not be described as an operation that did not happen.
No additional localStorage, sessionStorage or IndexedDB persistence is introduced
for credentials, pending intentions or private views. The existing server-set
HttpOnly session cookie remains the transport credential.

## Contract and compatibility

The paired access producer/validator/UI adds two mandatory closed fields:
`capabilities[].explanation` and `invitation_view.available_actions`. Older or
foreign shapes are rejected rather than accepted through an optional fallback.
Deploy the pair together. There is no new route, automatic profile downgrade,
credential format or change to `reading/1`.

The reading kernel, original material SQL, access migrations/roles, authority
evaluator, password verifier, canonicalization module and lockfile are unchanged.
The credential-free reader remains a separate retained profile. Existing
coordination, evidence and transport implementation are reused, not rewritten.

## Corrections made during implementation

- Preparation attempts using the wrong bootstrap person or extra surface IDs
  failed the existing database constraints. The fixtures were corrected to use
  the declared holder, real invitation-backed accounts and bounded surfaces;
  no database constraint was weakened.
- An early lost-response simulation used the browser tool's separate request
  client, which could not resolve the container-only hostname. It failed before
  exercising the intended property. It was replaced with browser-local real
  `fetch`; raw request-client errors containing synthetic request details are
  not publication evidence.
- The first receipt assertion expected an operation ID from issuance, contrary
  to the closed contract. The test now explicitly rejects that assumption and
  uses an actual withdrawal's operation receipt.
- The initial runner classified the new invitation-view mutation as an older
  invitation-suite mutation. That rejected invocation was not counted as a
  successful attack. The classification was corrected and D05 then caught the
  actual mutation on the final package.
- An inspection found that the authority snapshot intentionally lacks email;
  the new acceptance-offer lookup could therefore miss a restricted recipient.
  The admitted view now queries the required account fields directly. D16
  exercises the eligible/restricted/restored states. The acceptance operation's
  existing restriction guard was not changed.
- The first local standalone viewer-browser invocation had no installed default
  Playwright browser and failed at launch. The supported installed-Chrome
  invocation then passed all eight cases; no product assertion was bypassed.

## Correction pass · 2026-09-10

### Changes and preserved boundaries

- Share acceptance eligibility between the admitted view and execution, keeping
  the original ordered authorization, expected-revision, pending-state, current
  terms and recipient checks. The shared query reads only ID, restriction, office
  and whether an initial verifier is needed; it does not project credential data.
  Withdrawal faculty remains separate from lifecycle state. A stale withdrawn
  grant yields 409, a current withdrawn grant yields 403, and neither produces a
  false authority-escalation event.
- Retire only an uncertain **provisional login** when a valid current-session
  response establishes the authenticated context. Keep its earlier result
  explicitly unconfirmed. A failed observation cannot adopt the session. Other
  pending effects are not confirmed by a read, and switching tabs cannot erase
  them. Sign-out can proceed from the separately observed session.
- Keep the local-context check across the awaited exact-session observation.
  `verifySessionForView` checks on both sides of the wait; cancellation throws
  `AbortError`, while `StaleView` means an actually observed session mismatch.
  The unit counterexample removes the post-wait guard in memory and observes the
  incorrect continuation with the same successful session response.
- Use `Yes`, `No`, `Not verified` display labels without changing the protocol.
  The contract and proposed ADR state which absent actions are hidden and why
  acceptance remains visible but disabled. No new authority or disclosure is added.
- Give each execution a new evidence directory under
  `test-results/<suite>/<baseline-or-mutation>/<run-id>/`. `run.json` identifies
  that execution and records copying and cleanup. Reusing an ID fails instead of
  overwriting. Copying/logging failures cannot skip the owned-container cleanup.
  Existing directories remain untouched, including the earlier mixed baseline.
  Run the image's immutable build ID, not the reusable tag; record that ID with
  the result so another build cannot silently change the image under test.

add the run-ID component. CI already uploads the enclosing directories recursively.

## Login-notice lifetime correction

The unconfirmed-sign-in notice belongs to the separately recovered session, not
to the component's entire lifetime. Retiring it does not recover the original
missing receipt. `adoptSession` still arms the notice for a recovered provisional
login and does not clear it on ordinary refresh.

The only product change is in `AccessPanel.tsx`: clear the notice after a validated
successful login or logout, on an observed session mismatch, on confirmed absence,
or before adopting a verified replacement during refresh. The refresh comparison
uses the existing exact-session value, not account identity or revision. A failed
read and a same-session refresh retain the notice. Cleanup happens after a
confirmed transition, never merely on a button click or before a request returns.

### Directed coverage

- D20 retains its real lost-login-response experiment, blocked mode switch,
  unsuccessful observation, single login attempt and old-session 403 checks.
  It additionally checks preservation on same-session refresh and a later failed
  observation, removal on successful sign-out, and absence after a subsequent
  successful sign-in on the same document. The second login is counted separately
  after the original `loginCalls: 1` assertion; it is not a retry of the lost login.
- D22 and D23 replace the cookie with a real session from the same account and
  another account, respectively. Refresh adopts the replacement directly, without
  relying on the session-mismatch callback, and removes the earlier notice.
- D24 loses a real successful logout response. The notice remains while the client
  has no confirmation, even though an independent request observes old-session
  403. A subsequent current-session read confirms absence and removes the notice.
- D25 exercises the existing focus-triggered session-mismatch callback against a
  real replacement session. It removes both the authenticated view and its notice.

Every new transition starts with a positive recovered-session notice. Assertions
combine the notice count, authenticated-view count, browser login count and a
document-lifetime marker. No reload, fabricated successful response, increased
timeout or automatic retry makes these checks pass. New fixture accounts use the
real invitation and initial-credential routes, without changing rate limits or
spending another scenario's per-account budget.
