# INC-02 · T06 · Whole-journey acceptance

## Scope

Implementation on `card/INC-02-whole-journey`, based on `0ffe498` (T05).
This implementation is submitted for T06 publication after local verification.
ADR-037 remains proposed. Owner acceptance, final-head remote CI and merge are
separate steps; this document does not close INC-02 or authorize real data or
production use.

The principal journey starts without accounts, grants or acceptances. It uses
the exact predeclared master's real activation, an invitation it actually
issues, exact-email verification, acceptance of displayed terms, first password,
login, authenticated reading and withdrawal of that same received grant. The
recipient remains the same account throughout. The withdrawal removes reading
without logging the recipient out; ordinary recovery does not restore the grant.

## Implementation boundaries

### Initial administration is a product operation

`bootstrap.ts` is called only inside admitted first activation. It consumes a
preactivation declaration, checks its current basis with `InvitationAuthority`,
then atomically creates its person link and initial grants with account,
intention, proof consumption and evidence. Migration 004 adds immutable
declaration/activation records, uniqueness and a deferred evidence foreign key.
The runtime has SELECT on the declaration and no declaration write privilege.
No public route, global read permission, master approval or investiture is added.

The principal fixture declares three faculties: scoped `invite` exercise,
`read_people` exercise and `read_material` granting. Material exercise is acquired
only by the recipient's accepted invitation. Login/recovery are not bootstrap.
Expired, stale, absent and out-of-bounds declarations fail atomically. P07 applies
004 to a populated credential-only schema and compares all prior account,
proof, intention, evidence, person-link and grant rows: no retroactive gain.

### One identified artifact with the actual root composition

`ci/access_final_routes.mjs` copies the final routes and their applicable root
layout, `globals.css`, Next/PostCSS configuration, TypeScript configuration and
component/contract dependencies, including `src/instrumentation.ts` and its
typed configuration entry point, byte for byte. It verifies the inventory and
SHA-256 of both source and copy. The build then uses that real composition,
not the earlier simplified runtime shell. The suite checks its BUILD_ID after
every completed scenario; the runner records the immutable image identifier.

This bounded build intentionally excludes unrelated legacy routes. The retained
Next proxy matches `/api/v1/material/:path*`; it does not mediate the direct
session-bearing terminal. The ordinary whole-application build and retained
reader tests remain separate checks, not evidence inferred from this subset.

W01 tests the real Next startup configuration with valid/invalid controls.
W03 uses the same built artifact to test disabled/invalid access configuration
for both final routes, followed by a valid panel and actual reception operation.
It checks the real root's language and computed CSS. W18 checks keyboard focus
and narrow layout against that shell, not against a substitute layout.

### External declarations remain external

| Input | What the test supplies | What is not claimed |
|---|---|---|
| Preparation and reception | Attributable synthetic root, exact master address and controlled mailbox treatment | External accreditation, SMTP or production setup |
| Authority catalogs | Permission/scope/support definitions and declared person link | An implemented authority/catalog editor |
| Initial faculties | Immutable scoped declaration before any account exists | A grant INSERT replacing activation |
| Material and policy | Synthetic original, metadata and a policy instantiated against the produced recipient ID | Editorial approval, publication or a policy-management workflow |
| Nominal population | A declared display name/scope bound to the produced account for the census | Automatic naming, an unrestricted directory or census administration |
| Temporal invalidators | Existing control functions and deliberate short external policy deadlines | Repair of writer-free temporal conformity |

There are no fixture INSERTs for the principal journey's account, session,
acceptance, invitation or grants. Its expected effects are checked against SQL.
Separate bootstrap families use fresh deployments. The principal chain keeps
one recipient and grant; it stops after a failed prerequisite rather than
manufacturing later state. No rate budget is reset to make that chain pass.

### Timing, durable order and truth of the display

W11 pauses the actual browser material request after commit. In one assertion
it checks durable 200 evidence, zero transport observations, an idle SQL session
with no open transaction, zero material HTTP responses and zero rendered
originals. On release it checks exact original text and the later transport
observation. A screenshot is illustration, not the no-delivery oracle.

W15 forces an actual policy writer to wait on admission 20202, observes the
database lock, then checks both operation orders and a positive restored-policy
control. It does not infer serialization merely from elapsed time. W16 waits
past a short policy expiry before the last clock check and observes rejection.
W17 suspends after that check and records the actual delivery result. In the
identified baseline it observes 200 and original material after the deadline:
**the temporal requirement is violated; full temporal conformity is false.**

The existing A12, J18 and D12 experiments separately exercise session projection,
invitation effect and capability expiry. These are not proof that credential
issuance, effect commit and network handoff are universally atomic with time.

## Execution and evidence

Reproduce the new unit and full-journey checks:

```sh
npm run test:access:journey:unit
npm run test:access:journey
node ci/access_runtime_check.mjs --journey --mutation=drop-bootstrap-materialization
```

Other directed mutations are `drop-bootstrap-root-binding`, `drop-bootstrap-revision`,
`drop-bootstrap-exercise-bound`, `drop-journey-reading-authority`,
`drop-journey-evidence` and the cleanup probe `early-failure`. A mutation must
produce its intended assertion failure, not merely exit nonzero. The chain
stops at a failed prerequisite; its shortened entry count is not a skipped
protection or a conformity statistic.

Every runtime invocation writes a unique directory under
`test-results/access-journey/<variant>/<runId>/`: `run.json`, `run.log`, the
composition manifest, journey observations and selected screenshots. Earlier
observations are not overwritten. CI uploads the directory with `if: always()`.
The runner uses its built image ID, unprivileged container-local HTTPS/browser
and PostgreSQL, no external network, explicit time bounds and owned cleanup.
Trust certificates use a per-environment nickname inside the disposable
container's NSS store and are removed by that environment; the host is untouched.

## Directed bootstrap and composition correction

This pass changes the test/build boundary, not the access service, authority
evaluator, SQL migrations, public contracts, UI components, startup hook or
configuration implementations. ADR-037 remains proposed. No commit, publication,
remote CI or increment closure is part of this pass.

### Current-root binding

P08 installs a valid initial declaration, changes only the current preparation
root and increments the deployment revision, then obtains a fresh activation
proof. Before activation it checks that the proof and deployment both have
revision 2, while the declaration's root differs and email/holder still match.
The expiry and other authority conditions remain valid.

Its joint observation requires the generic public `503 technical_failure`, zero
accounts, grants, person links and bootstrap activations, an unconsumed proof,
and the internal `BOOTSTRAP_DECLARATION` failure. The internal cause is not added
to the HTTP response. P01 remains the unchanged-root positive control.

`drop-bootstrap-root-binding` removes only that root comparison from an owned
source copy. P08 then observes 200, one account, three grants, one person link,
one activation and a consumed proof. Only P08 and its parent fail (26 passed,
2 failed entries); all principal-journey scenarios still pass. This distinguishes
the intended binding from rejection of an obsolete proof or invalid setup.
Run: `access-t06-2a368165-89c5-4737-a986-2d92e22d0f92`.

### Source inspection before Docker filtering

`withSourceComposition` inspects the original checkout before invoking the Docker
build. The allowlist covers the known app-root entries, both access segments,
and framework entry points at the project root and under `src`. Unknown entries
fail preparation rather than becoming automatic exclusions. The excluded proxy
is pinned to its reviewed source, normalizing only line endings; a changed
matcher or other proxy change requires reclassification. This is a bounded
known-composition guard, not a general Next configuration interpreter.

The source record contains paths and byte fingerprints for included and excluded
files, with explicit exclusion reasons. A unique run owns the record. BuildKit
supplies it as a read-only input outside the filtered context; this is public
build metadata, not a secret credential. A separate SHA-256 build argument binds
the record and changes the build cache key when that record changes. The builder
matches the filtered included files against the original record before copying
them, then verifies the copied bytes. The runner rechecks the source after the
build; a changed exclusion cannot leave a successful but stale attestation.

The output includes the original `source-composition.json` and the resulting
`composition.json`. W01 checks their binding against the digest retained in the
image. It also invokes the copied instrumentation entry point independently of
`next.config.mjs`, with valid settings, invalid settings and a forbidden bind
address. The actual bounded Next build includes that same hook and dependency.

The 12 unit tests retain the original selector and byte-copy checks and add
positive source admission, six unclassified convention negatives, widened proxy
rejection, changed-exclusion rejection after the build callback, and the binding
between a filtered copy and its pre-filter record. Rejections before preparation
jointly check the error and zero build-callback calls. Copy checks also cover
instrumentation and its typed configuration dependency.

Three executable guard mutations act only on a temporary module copy:

| Mutation | Discriminating unit result |
|---|---|
| `drop-root-classification` | 9 pass / 3 fail: the root template, access loading and material error cases wrongly call the builder |
| `drop-proxy-classification` | 11 pass / 1 fail: the widened proxy wrongly calls the builder, even with a misleading matching comment |
| `drop-source-recheck` | 11 pass / 1 fail: an excluded sibling changed during the build no longer rejects |

requires one exact replacement site and reports its owned temporary-directory
cleanup. The captured local transcript is under
`test-results/access-journey/composition-checks/correction-135e21aac5bb68/run.log`.

## Remaining boundaries

- R24 remains an observed temporal failure, reproduced by W17. Cooperating-writer
  success does not repair clock-to-transport atomicity. This is explicit technical
  work before real data, not a check to postpone until that boundary is crossed.
- [BROWSER-I03 and BROWSER-J19](INC-02-T03.md#tracked-browser-follow-up) remain
  open with their existing evidence and causal closure criteria. Another green
  run does not resolve their causes; a recurrence must be investigated.
- Catalog, investiture, resolution, material publication and nominal-population
  producers not implemented here remain external fixtures or later consumers.
  This journey does not certify their external truth or production admission.
- PostgreSQL 16 remains the replaceable isolated trial realization. No real
  account, real corpus, external mail or production identity service is enabled.
- Acceptance of this experimental deliverable, full contract conformity and
  authorization for the next increment are three separate decisions.
