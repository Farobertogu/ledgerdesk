`ReadingPersistencePort` refines the preparation/transport obligations documented
with the T02 ports. It joins preparation and prior evidence inside one coherent
commit instead of calling an independent evidence writer with a second connection.
It does not claim that a method signature proves durability or safe delivery. The
older broad `ReadingMaterialPort` is not wired into the Next endpoint by this step.

## Behavior

The launch configuration fixes deployment, scope, subject, surface, purpose and
generation. Requests cannot supply these through cookies, headers or query fields.
Disabled service returns 403 without creating a database adapter. Malformed launch
configuration fails startup. Only loopback listening is supported.

Policy evaluates the exact context and action at the preparation instant. Missing
applicable unit policy permits explicit inheritance; denial or indetermination
does not. An absent grant is never public access. Multiple applicable grants in
one tier are indeterminate, not an invented union of permissions.

The five disclosure levels remain distinct:

- NONE and local indetermination contribute no public identity or signal.
- EXISTENCE contributes only the list's generic Boolean signal, never a row or
  confirmation in exact detail.
- REFERENCE exposes only permitted metadata and the exact pair.
- EXCERPT exposes only declared literal substrings and permitted fragment locators.
- CONTENT exposes the exact stored original and permitted metadata.

Every field uses an allowlist. A historical or non-public item requires its actual
editorial state and specific conditions together. If an excerpt cannot reveal an
indispensable exception, only an explicitly declared faithful lower projection is
eligible. The code does not infer semantic completeness from prose: those
prerequisites are synthetic seed declarations to be supplied by the later editorial
path. A visible invalid profile fails rather than silently truncating or rewriting
the source. Hidden local policy problems stay local.

List order follows ordinal unit ID then version ID. The bounded trial emits all
eligible references or fails; 16 is an experimental profile limit, not a product
limit. Detail selects an exact stored pair and never redirects to a newer version.
Policy headers and permitted payloads share one snapshot. Hidden originals are not
fetched just to discard them afterward. No cache or serialized prepared DTO grants
permission for another read.

## Storage and exactness

The cluster is created from `postgres:16` with no historical bind mount, shared
volume or network. It listens on a randomly allocated loopback port and uses random
test credentials that are not written into the repository. It initializes only
the new schema; historical migrations and database reset scripts are not executed.

Originals, metadata, fragments and policy JSON preserve the decoded public strings.
Canonical JSON-encoded unit/version keys permit exact lookup of opaque identifiers
containing escaped control characters. SQL does not unescape those keys. Tests
cover NUL, a lone surrogate, emoji, combining accents, CRLF, spaces and inert HTML;
metadata and the exact URL-requested key round-trip too. This is not an uploaded
file binary-preservation claim.

The runtime role is not the schema owner and cannot create databases, roles, public
objects or acquire privileged/legacy roles. `PUBLIC` has no schema/function access.
The reader cannot rewrite originals/evidence, mutate policies or invoke control
writers. The writer has no table mutation grant; it executes only the two explicit
definers with `search_path=pg_catalog`.

The tests inspect effective permissions and execute the actual retained
`withAppSession` boundary against the fresh synthetic cluster. Its `app_rw` path
cannot access the new schema, and the new reader cannot enter `app_rw`. The five
retained SQL-reading pages are `/portal`, `/queue`, `/supervisor`, `/tickets/[id]`
and `/promotion`. Their shared SQL boundary is tested, not five rendered legacy
browser journeys. Static imports are checked in both directions, including
`src/alg` and old components. No historical route was removed by T04; inaccessible
removed-route testing is therefore not claimed.

## Evidence and actual delivery order

1. The sole deployment owner acquires session admission.
2. A `REPEATABLE READ` transaction checks current control, five treatment gates and
   generation, resolves policy and prepares the exact projection.
3. It inserts private access evidence and completes a known synchronous commit.
4. The same session retains admission with no SQL transaction open. The terminal
   checks observed control/expiry and transfers the public response.
5. It records the observed outcome and only then releases admission.

Evidence contains context, action, restriction revision, requested pair, policy
causes and intended result, not originals or credentials. The public body contains
none of this private wrapper. Transport status is recorded only if headers were
actually handed off. Unknown byte counts remain null. A preparation abandoned
before any handoff records zero transferred bytes separately.

The writer inventory is `replace_policy` plus `set_control` changes to generation,
activation, capture, processing, conservation, trace and destination. Every one
takes the same PostgreSQL advisory lock. Tests observe an actual writer lock wait
between commit and handoff, release the response, then observe the writer commit
and a newly refused read. Requesting revocation is distinct from its committed
effect. The guard is deliberately coarser than production throughput would need.

An INSERT or deferred-COMMIT failure releases no material and returns neutral 503.
An abort after evidence commit records interruption without claiming reception.
An observed SQL-session loss destroys active responses. If observation storage
fails after a response, prior evidence remains but the result is unresolved; the
terminal stops further delivery. Restart preserves stored originals, restrictions
and evidence. Administrative destructive fault injection occurs only inside the
new disposable test cluster.

Evidence `result_status` records the prepared decision, not proof of the eventual
HTTP result. For example, if observing an expired, abandoned preparation fails,
the later 503 observation can refer to evidence whose intended status was 200.
This does not mean a 200 body was sent. Observation inserts are not guaranteed
exactly once: a lost acknowledgement followed by retry may leave multiple rows
for one receipt. Treat that history as potentially uncertain, not as multiple
successful deliveries or a reconstructed byte count. This step does not add an
idempotent observation protocol.

## Measured scope and limitations

The actual emitter is Node HTTP on loopback, with no proxy, compression, cache or
application streaming. Admission extends through Node `finish`, not through a
database commit or a returned JavaScript response object. `finish` is not human
receipt or a proof that remote/kernel buffers are fenced.

The writer-free expiry experiment pauses the entire JavaScript emitter after its
time check. In the recorded run it returned HTTP 200 with material after the
deadline. Its diagnostic says `fullTemporalConformity: false`. A green experiment
means this limitation was observed and reported, not that late delivery is safe.
Expiry already observed before the final check re-prepares to a neutral refusal;
that does not eliminate the subsequent pause window or establish clock alignment.

Likewise, lifetime ownership prevents two cooperating live terminals; it does not
prove physical fencing after arbitrary database/network/process loss. Root and
superuser maintenance can bypass ordinary writers and must remain offline. There
is no production ingress, schema migration, cluster failover or operator-control
proof in this step. These limits prevent any claim of full temporal compliance.

The pre-handoff `available()` check is defence in depth. Observed PostgreSQL loss
also destroys active responses, so a reset connection alone cannot prove this
check executed. The directed test now inspects the observer boundary: after control
loss it must reach release without `handoff`, `finished` or `interrupted` events.
Deleting the check must fail that assertion. An HTTP 503 is not required from an
already destroyed socket, and this event assertion is not physical buffer fencing.

The neutral-refusal timing protocol is fixed before results: four classes, 12
warmup rounds, 128 measured requests per class, balanced rotating order, 999
permutations, family alpha 0.01 with six comparisons, and absolute Cliff delta at
least 0.33 to flag a signal. A deliberately shifted distribution must be detected.
Bodies, lengths, status and headers are also compared exactly. A passing finite
sample does not establish constant time or universal noninterference. Different
populations, load, network topologies and side channels remain unproven.

In the initial T04 delivery's recorded complete run, the four medians were 8.412 ms (absent),
8.634 ms (NONE), 8.475 ms (local indetermination) and 8.588 ms (EXISTENCE).
No comparison met the predeclared signal rule; the shifted control did. These
are observations of that run, not thresholds to tune future runs against.

One setup attempt failed without a specific cause retained by the former generic
diagnostic. It is not counted as a passing run. Setup errors now retain bounded
diagnostics with credentials redacted. Later complete runs created fresh clusters
and passed; they do not explain that earlier setup failure.

## Reproduction and review

Run `npm run test:reading:service` with Docker's Linux engine available. The harness
creates, validates, seeds and tests a fresh project named `ld-reading-t04-<random>`.
It verifies its own container labels, loopback binding, mount and network before
testing and before cleanup. It removes only that project's disposable test data;
it does not stop Docker or touch existing historical containers/volumes.

Run the entire file. A name filter matching only a nested scenario can skip the
parent that creates the cluster and report a passing file entry without running
any of its 24 scenarios; that is not evidence of service behavior.

Observer/event gates have a 15-second bound and are released after each subtest.
Cleanup is registered immediately after cluster creation, before connecting the
writer or seeding data. Terminal, writer and administrative connection closes are
bounded; an earlier failure does not skip the remaining cleanup steps. Docker
removal validates project ownership and checks containers, volumes and networks
afterward. Successful removal emits `PG_TRIAL_CLEANED`; cleanup failures remain
test failures, not successful timeouts. These controls cover handled failures in
the test process, not a machine crash or an unavailable Docker daemon.

`npm run test:reading:lifecycle` exercises the gate and cleanup helpers without
Docker, including a missing event, a parked observer, a failed assertion, stalled
closes, continued cluster cleanup and a failed removal. The `reading` job runs it
before the real service suite.

`npm run start:reading:service` is the separate explicit entry point. It requires
the synthetic gate/context variables plus `LEDGERDESK_READING_PG_URL`,
`LEDGERDESK_READING_PG_PORT` and optionally `LEDGERDESK_READING_HTTP_PORT` (3002 by
default). Only the dedicated reader credential for an initialized synthetic
cluster is accepted. This is not a command to connect to a historic database.

Review the actual working-tree files, including untracked new files; a normal
`git diff` alone omits them. Prioritize projection fidelity, effective privileges,
evidence-before-handoff, writer ordering, neutral refusals, exact persistence and
the stated temporal limitations. Do not turn the experiment's passing assertion
into a full-contract acceptance.

T05 remains separate: compose the viewer with the final admission owner, exercise
the UI→HTTP→PG journey and evaluate all 24 LR-AC groups at their stated scopes.
Prior-stage UI success and T04 standalone service success are not that journey.
