# INC-02 T03 · Revisioned invitations and ordinary accounts

## Scope and acceptance boundary

This delivery implements the invitation lifecycle against actual isolated
PostgreSQL 16, the existing HTTPS terminal and the minimal Next UI. It extends
T02 without replacing its activation, session, password or transport mechanisms.
The implementation is a synthetic construction candidate for review, not
production access, completion of INC-02 or acceptance of
[ADR-034](../adr/ADR-034-revisioned-synthetic-invitations.md), which remains proposed.

An invitation proposes a gain; email verification does not accept it. Acceptance
uses the current revision, current grantor authority and the actual recipient
proof. It reuses or creates one account, records one acceptance, persists the
exact grants, consumes the proof and writes evidence atomically. Neither the
master office nor an invitation establishes unrestricted material authority.

## Revision, intent and lock rules

`amend_invitation` replaces only the grants of the same pending invitation. It
requires its current revision, revalidates grantor authority, scope and local
incompatibilities, increments the revision and retains the earlier terms.
Recipient, family and expiration are not editable. Existing email proof remains
email proof: it is not consent to new terms. The stale-acceptance negative keeps
the invitation and proof alive and expects `revision_conflict` specifically.

New intent payloads include contract, variant, typed path and parameters, empty
query, body and the body's revisions. Keys are ordered by Unicode scalar value,
not UTF-16 units or locale; strings are not normalized. Arrays retain order,
absence differs from null, and exact safe integers exclude fractional/exponent
lexemes. Decoding rejects invalid UTF-8, duplicate keys and unpaired surrogates.
`JSON.stringify` is used only for JSON string escaping, not object ordering.

The namespace does not include target or revision. Within the single bound
deployment, a session or verified recipient uses a stable exact-email digest;
unverified support treatments use their persisted flow. Changing an object
under the same client intention conflicts. A repeated successful request
reauthorizes its receipt and never replays a credential. A response lost after
commit is reconciled without a duplicate account or grant. Operation-result
lookup checks the stable principal and current permissible projection.

The additive migration marks old T02 receipts `legacy_t02`. They are compared
with the original algorithm; only new receipts use `canon_m09_1`. A retained
successful challenge does not send another email when retried.
J01 applies the migration to an existing master account. J02 separately inserts
an old-format successful receipt to exercise the legacy comparator; this fixture
is not an archive of historical production traffic.

Acceptance selects the exact proof identifier within its owning flow, separately
from the target invitation. This keeps the principal independent of the target
and permits two verified invitations in one flow without selecting the latest
unrelated proof. Initial-credential receipts can also be inspected under their
own still-verified flow; an unrelated recovery flow cannot read them.

Object discovery selects lock keys only. The decision rereads facts after locks,
inside Repeatable Read. The lock sequence is: deployment admission, sorted
effective object lock identifiers, decision snapshot, effect/evidence commit,
terminal handoff, observation and release. Hash collisions share a lock and
cannot reverse its acquisition order. The reverse-overlap test uses two actual
connections without acquiring the deployment guard, so that guard cannot hide
an incorrect order. The test establishes the ordering, not exhaustive deadlock
freedom under all future operations.

T02 and T03 also share flow/session lock namespaces. Login consumes its
provisional flow and must not race an invitation acceptance using that flow,
even when the login targets a different account. J23 observes the actual
ungranted PostgreSQL flow lock, not merely an elapsed delay or a global guard.
The UI aborts pending work and clears invitation state on an identity change;
J24 delays the text of a real response and confirms it cannot reappear after logout.
The invitation workspace waits for initial account reception before opening
another flow. J19 holds that first request and checks the disabled control, then
checks the actual login response. An earlier browser run timed out waiting for
the signed-in heading; a diagnostic rerun passed. That earlier timeout was not
independently attributed to the reception race, and is not rewritten as a pass.

## Authority, continuity and account lifecycle

- Positive grants require invitation exercise and the specific **granting**
  faculty, compatible family and subordinate scope. Exercise is not granting.
- The granting options shown in the UI come from the server's current inputs.
  Unknown catalog entries, scopes or required declarations fail closed.
- Domain-assumed support is distinct from issuer-dependent delegation. The
  continuity test first creates both grants, removes actual issuer authority,
  then checks that only the independently assumed grant can issue another proposal.
- Person linkage has an attributable source. Accounts explicitly linked to the
  same person cannot bypass a declared local separation rule. Its check includes
  both grants and declared functions and never silently withdraws existing powers.
  A broad grant/function cannot bypass a rule over a narrower overlapping scope.
  An `unlinked:` identifier only correlates an account lacking that determination;
  it does not establish a natural person's identity or independence from others.
  No independent-person authority operation is opened by this delivery.
- A required function declaration is checked and its expiry enters the deadline.
  Consumed declarations appear in the terms/evidence as registered and not
  externally accredited. No accreditation endpoint or truth certification exists.
  Dependent support also requires the source grant's current declaration where
  applicable; a retained grant row alone is insufficient.
- The expiration of a proposal limits acceptance, not the life of every grant.
  Resulting grants carry the displayed support-bound lifetime; current support,
  scope and withdrawal remain conditions even before that timestamp.
- Withdrawal of a pending invitation cannot undo an accepted grant. Permission
  withdrawal is a separate revisioned effect without recipient consent. A denied
  attempt does not close the session; out-of-scope withdrawal records the need
  for competent-domain handling, not a fabricated escalation workflow.
- Initial credential establishment is tied to the accepted account/flow and
  requires no prior verifier. If the flow is lost, ordinary recovery reaches the
  same account. Recovery rotates the verifier/session generation, not permissions.
  Earlier recovery proofs cannot overwrite a later credential change.

## Privacy and receiver limits

Locators are selectors, not authorization. Unverified invitation views return
the same unavailable projection. Challenge reception returns generic `accepted`
and performs a same-shaped proof write for eligible and ineligible locators;
the latter has no invitation binding and cannot verify or accept anything.
Codes are sent only to the exact nominated address through the controlled
mail adapter. No debug inbox, code in HTML/URL or external SMTP is introduced.

Challenge sending is bounded per (locator, socket peer), with the configured
cooldown and attempt window. A new flow cannot reset that pair's counter.
The adapter is not a durable mail queue. Distributed sources, mailbox flooding,
real deliverability and production anti-abuse capacity are not solved here.

J20 compares status, body, all response headers and timing for pending, absent
and withdrawn invitations, separately for view and challenge reception. Each
class has 12 warmups and 128 samples; each comparison includes a shifted control
that must be detected. The controlled fixture clears the invitation-mail rate
counter before each measurement to isolate the admitted, unthrottled path.
This is not a proof about throttled or arbitrary production workloads, nor a
constant-time guarantee. No connection or measured sample is excluded.

Authority inputs are bounded to 1,000 rows per participating table, 32 scope
ancestors, 4,096 option combinations and 64 projected options. Exceeding a bound
fails rather than silently truncating a complete answer. These are trial limits,
not requirements on an organization's eventual size. The UI creates one proposed
grant at a time with a five-minute trial acceptance window; the API supports up
to 32 grants and the configured invitation lifetime. No production default is set.

Run from the repository with the installed dependencies and Docker available:

```sh
npm run test:access
npm run test:access:canonical
npm run test:access:runtime:unit
npm run test:access:browser
npm run test:access:runtime
npm run test:access:invitations
npm run typecheck:app
node ci/access_boundary_check.mjs
node ci/reading_boundary_check.mjs
```

The runtime runner builds the pinned Linux image, owns a uniquely labelled
container, starts a fresh local PG16 cluster and uses container-only HTTPS trust.
It neither edits the host's name/certificate configuration nor opens a host port.
The suite has a four-minute bound, the runner five minutes, plus bounded cleanup.
Cleanup checks ownership before removal. This narrows known failure modes; it
does not claim cleanup can survive a killed Docker daemon or machine failure.
An initial revision-mutant run exposed an open fixture transaction after a
failed assertion and was stopped. Per-case rollback now releases that transaction
before later cases, and final cleanup rolls it back before closing the terminal.
The earlier interrupted log remains local evidence, not a successful cleanup test.

## Integration and remaining work

The additive migration is tested over an existing master and retained receipts.
Ordinary account insertion requires a matching pending invitation even at the
database boundary; complete proof, acceptance and authority checks remain the
trusted service's responsibility. Runtime cannot rewrite catalogs, investiture
inputs, account identity/office/restrictions or immutable evidence. No existing
user database, legacy schema, old Git history or retained UI is deleted.

T02's isolated test reset uses `TRUNCATE ... CASCADE` only inside its owned fresh
fixture because new tables reference accounts. Assertions are retained. The
credential-free reading profile and its negative tests remain separate.

On this Windows checkout, the optional Playwright headless-shell executable was
absent. The first local reading-browser launch failed before exercising the
viewer. Its documented `READING_BROWSER_CHANNEL=chrome` option uses installed
Chrome for the local rerun; no browser installation or trust bypass is needed.
The invitation journey uses the pinned container browser, independently of that
host selection. CI retains its existing Chromium installation step.

`reading` CI includes the new canonical and invitation suites and uploads their
evidence even on failure. Remote execution of this unpublished change has not
been performed. The previously reported intermittent reading I03 failure has
no established cause; an occurrence must be investigated, not presumed unrelated.
Both that failure and the earlier invitation sign-in confirmation timeout must
be disclosed when publishing this change. A recurrence should be investigated
for shared causes, including resource contention, without treating that
hypothesis as an established explanation or ignoring a failing check.

Full temporal conformity remains false. The directed deadline case is observed,
not a proof for every writer-free expiry. Session-derived material reading,
broader authority/independence surfaces, restored-snapshot reconciliation and
administration UI remain later tasks. This delivery does not certify real
organizational authority, production identity or a real-data receiver profile.
